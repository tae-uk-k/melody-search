세 방식 비교

C++ 실측값. 데이터 1천~100만 항목, 입력 16칸, 반복 측정 중앙값.

결론: 검색은 체이닝 해시, 메모리는 정렬 배열이 유리

  • DB에 있는 곡을 찾으면 해시가 데이터 크기와 상관없이 항상 가장 빠름. 100만 항목에서 순차 배열보다 약 33만 배.
  • DB에 없는 곡을 작은 데이터(1천~5천 항목)에서 찾으면 정렬 배열이 더 빠름.
  • 해시는 정렬 배열보다 구축이 약 3.6배 느리고 메모리를 약 65배 사용.
  • 그래서 대부분의 상황에서는 정렬 배열이 가장 균형 잡힌 선택.

검색 ①: DB에 있는 곡을 입력할 때

DB에 있는 곡에서 16칸을 그대로 잘라 입력. 답은 항상 16칸 전체 일치.

결과: 해시가 모든 크기에서 가장 빠름

  • 세로축은 10배씩 커지는 로그 눈금.
  • 100만 항목에서 순차 배열 522ms, 정렬 배열 10µs, 해시 1.6µs.
  • 조옮김·길이 2배·가운데 음 하나 변경을 한 변형 구절도 같은 모양. 100만 항목에서 정렬 배열 8.9µs, 해시 1.1µs.

왜 이렇게 나왔나

순차 배열: 데이터에 정비례 O(N)

하는 일 입력 16개 시작 위치 × DB의 모든 시작 위치를 하나씩 짝지어 비교.

그래서 100만 항목이면 16 × 100만 = 1,600만 쌍. 데이터가 1,000배면 비교도 1,000배라 그래프가 곧은 오르막(실측 약 860배).

정렬 배열: 조금씩 증가 O(log N)

하는 일 입력 조각 16개마다 정렬된 배열에서 들어갈 자리를 이진 탐색. 그 자리의 위·아래 이웃만 비교.

그래서 이진 탐색 횟수는 1천 항목에서 약 10번, 100만 항목에서 약 20번. 데이터가 1,000배 늘어도 일은 2배 정도만 늘어남.

체이닝 해시: 거의 일정 O(1)

하는 일 길이를 8 → 12 → 14 → 15 → 16 순서로 좁히며 "이 길이로 일치하는 조각이 있나?"를 해시표에 물어봄. 칸 번호를 계산해 바로 찾아감.

그래서 있는 곡은 매번 "있음"이라 첫 일치에서 바로 다음 길이로 넘어감. 질문 5번 × 칸 몇 개 확인이 전부라 데이터 크기와 상관없음.

이론과 실측이 갈라지는 곳: 정렬 배열

  • 점선은 1천~2만 항목 결과로 그린 O(log N) 예측선. 20만 항목까지는 실측이 예측선을 따라감.
  • 50만 항목부터 예측보다 2배 이상 느림. 100만 항목에서 예측 약 4.4µs, 실측 10.0µs.
  • 원인: 데이터와 색인을 합친 크기가 CPU의 L3 캐시(24MB)를 넘음. 이진 탐색은 멀리 떨어진 칸을 건너뛰며 읽어서, 캐시에 없으면 느린 메인 메모리까지 다녀와야 함.
  • 해시는 같은 구간에서도 평평함. 칸 몇 개만 읽어서 캐시 밖에 있어도 영향이 작음.
  • Big-O는 비교 횟수만 세고, 데이터가 메모리 어디에 있는지는 고려하지 않음.

검색 ②: DB에 없는 곡을 입력할 때

DB에 없는 곡에서 16칸을 입력. 16칸 전체가 맞는 곡은 없고, 짧게 겹치는 곡만 있음.

결과: 작은 데이터에서는 정렬 배열이 더 빠름

  • 1천~5천 항목: 해시 39~88µs, 정렬 배열 22~30µs. 정렬 배열이 최대 3배 빠름.
  • 1만 항목부터는 두 방식이 4~37µs로 비슷하게 움직임.
  • 두 방식 모두 있는 곡(1~10µs)보다 느리고, 데이터가 작을 때 오히려 더 느림.

왜 데이터가 작을수록 느릴까: 확인할 후보가 많음

  • 데이터가 작으면 가장 길게 겹치는 부분이 평균 2칸 정도로 짧음.
  • "음 → 쉼"처럼 2칸짜리 멜로디는 여러 곡에 흔함. 그래서 최장 길이로 겹친 후보가 1천 항목에서 질의 하나에 2,095개.
  • 답에는 겹친 곡을 모두 적어야 해서 후보를 전부 확인해야 함. 1만 항목부터는 더 길게 겹치는 곳이 생겨 후보가 50~300개로 줄어듦.

왜 해시가 정렬 배열보다 느릴까

① "없음" 답은 끝까지 확인해야 함

해시는 길이를 바꿔 가며 "이 길이로 일치하는 조각이 있나?"를 물어봄. "있음"은 첫 일치에서 바로 멈추지만, "없음"은 입력 조각을 전부 다 찾아봐야 확정.

있는 곡은 답이 16이라 질문이 모두 "있음". 없는 곡은 답이 2~4라 8칸, 4칸, 3칸 질문이 "없음"이 되어 매번 끝까지 확인.

② 후보 하나를 확인하는 일이 더 많음

해시는 해시값이 같은 후보를 원래 음높이·길이로 다시 비교해 진짜 일치인지 확인(길이 비율 계산 포함).

정렬 배열은 이미 만들어 둔 변화 글자 번호를 2개 정도만 비교하면 됨. 후보 2,000개면 이 차이가 그대로 쌓임.

③ 정렬 배열은 후보가 한곳에 모여 있음

정렬 배열에서는 앞부분이 같은 조각끼리 붙어 있어서, 들어갈 자리에서 위·아래로 쭉 읽으면 후보를 다 모음.

해시도 같은 칸에 모이지만, 칸을 찾고 체인을 따라가는 과정이 길이마다 반복됨.

구축 시간

이론은 해시가 빨라야 하는데, 실제는 정렬 배열이 3.6배 빠름

  • 이론상 정렬 배열 구축은 O(N log N), 해시는 O(N). 해시가 더 빨라야 함.
  • 100만 항목에서 실측은 정렬 배열 429ms, 해시 1,565ms.

왜 이렇게 나왔나

정렬 배열: 시작 위치 하나에 조각 1개

하는 일 모든 시작 위치를 (블록 번호, 시작 위치)로 배열에 넣고, 변화 글자 순서로 정렬.

그래서 비교 횟수는 약 N × log₂N. 100만 항목이면 log₂N ≈ 20이라 위치 하나당 비교 약 20번. 비교도 대부분 앞 글자 몇 개에서 결판남.

체이닝 해시: 시작 위치 하나에 조각 32개

하는 일 시작 위치마다 길이 1~32 조각의 해시값을 계산해 길이별 해시표 32개에 하나씩 넣음.

그래서 위치 하나당 저장 32번. Big-O에서는 상수라 지워지지만 실제로는 32 > 20. 100만 항목 정도에서는 log N보다 상수 32가 더 큼.

메모리 접근 방식 차이

해시는 해시값에 따라 표의 아무 칸에나 써야 해서 매번 메모리 여기저기를 건드림(캐시 미스).

정렬 배열은 작은 배열 하나 안에서 자리만 바꿔서 캐시에 잘 들어감.

항목 1개당 구축 시간: 해시는 캐시를 넘는 순간부터 증가

  • 항목 수로 나눈 구축 시간. 이론상 O(N)이면 수평선이어야 함.
  • 해시는 1만 항목까지 항목당 약 0.4µs로 수평. 5만 항목 근처에서 색인이 L3 캐시를 넘으면서 100만 항목에서 1.6µs로 4배 증가.
  • 정렬 배열은 log N만큼 천천히 늘어 0.1µs에서 0.4µs.

메모리

100만 항목에서 해시 색인은 정렬 배열의 약 65배

  • 정렬 배열은 시작 위치마다 (블록 번호, 시작 위치) 하나만 저장. 조각 내용은 복사하지 않아서 항목당 8~14바이트.
  • 해시는 시작 위치마다 조각 32개를 저장하고, 조각마다 해시값(8바이트)과 위치(4바이트)를 넣음. 12바이트 × 32개 ≈ 384바이트에 칸 시작 위치 표까지 더해 항목당 약 550바이트.

치명적 맹점: 전체 데이터면 해시 색인 16.7GB

  • 전체 3,048만 항목을 해시로 올리면 실험 PC 메모리(3.9GB)의 4배가 필요. 그래서 100만 항목까지만 실험.
  • 보완책: 검사할 길이의 조각만 그때그때 저장. 메모리는 1/32 수준이 되지만 검색마다 색인을 다시 만들어야 해서 검색이 느려짐.

어떤 걸 고를까

    가장 빠른 자료구조가 항상 가장 좋은 선택은 아님. 검색 횟수와 메모리 여유에 따라 달라짐.
